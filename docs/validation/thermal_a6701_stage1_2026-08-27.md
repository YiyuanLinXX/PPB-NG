# FLIR A6701 Stage 1 hardware validation — 2026-08-27

## Scope and safety

The thermal camera was connected by Ethernet and a FLIR Blackfly S RGB camera was
simultaneously connected by USB. All camera selection used exact `DeviceID`; no
index-based selection was used. The RGB camera was enumerated but never initialized.

The initial inventory used the transport-layer node map only. The detailed thermal
probe initialized only the exact thermal device and performed no feature writes or
acquisition. The acquisition probe subsequently preserved all current feature values,
captured 20 volatile frames, wrote no image files, and stopped/deinitialized cleanly.

## Network

- Dedicated adapter: `Ethernet 3`, Intel X550 #2, interface index 6, 1 Gbit/s.
- Existing host address retained: `192.168.4.150/24`.
- Operator-added secondary address: `169.254.10.1/16`.
- Camera address reported by Spinnaker: `169.254.10.244/16`.
- Two ICMP probes succeeded with less than 1 ms response time and 0% loss.

Before the secondary address was added, Spinnaker correctly rejected initialization
with `Camera is on a wrong subnet [-1015]`.

## Read-only A6701 state

- `Width=640`
- `Height=513`
- `PayloadSize=656640`
- `PixelFormat=Mono16`
- `IRFormat=Radiometric`
- `AcquisitionMode=Continuous`
- `FrameSyncSource=Internal`
- `FrameSyncMode=Integration`
- `FrameSyncPolarity=ActiveHigh`
- `TriggerMode=FreeRun`
- `TriggerSource=Internal`
- `Ready=1`
- `FPACold=1`
- `GevCCP=ControlAccess`
- `CorrectionDigitalEnabled=1`

`DeviceTemperature=-199.37` is a physical FPA reading, not a sentinel. The active
`DeviceTemperatureSelector` is `FPA`; the manual states that the cooled FPA nominal
setpoint is 77 K (about -196.15 C), so this value is plausible and agrees with
`FPACold=1`. `AcquisitionFrameRate` was not readable under that node
name and needs a targeted feature-node investigation before production rate control.

## Remaining work before a production thermal run

The current production thermal node is intentionally external-frame-sync-only and
refuses to arm without verified external-sync semantics. The connected camera is now
operating in internal free-run mode and has no external trigger cable. A separate,
explicit internal/free-run production mode must be implemented and tested without
weakening the fail-closed rules for the future external-sync mode. Configurable 2 Hz
capture behavior also needs validation against this firmware's actual feature nodes or
an explicitly documented software sampling policy.

## External-sync ROS 2 update (later on 2026-08-27)

The UNO R4 D12 to A6701 SYNC IN path was subsequently validated at 2 Hz. A dedicated
ROS 2 test node now records the exact camera payload, Arduino pulse sequence/tick,
camera frame ID/timestamp, host monotonic receipt time, and an allow-listed calibration
snapshot. A 22-frame recovery suite passed both a four-second commanded trigger pause
and an UNO host-watchdog stop/restart without reopening the camera. A separate normal
run produced 11/11 one-to-one pulse/frame associations; camera timestamp intervals
were 500.360565 to 500.401995 ms. Absolute UTC remained deliberately `UNSYNCED`
because GPS/PPS was absent.

# Software recovery investigation (2026-08-27)

- Windows process inspection found no surviving PPBNG, Spinnaker, SpinView, or Research Studio process after the failed focus-validation attempt.
- The exact-device `DeviceReset` command was executed once. The transport rediscovered the A6701 after about 15 seconds, but A6701-specific nodes remained unavailable (`CameraModel` read as `n]`; `Ready`, `FPACold`, geometry, temperature, and frame-sync nodes were unreadable).
- A fresh process-local `GENICAM_CACHE_V3_0` directory reproduced the same result, excluding the existing GenICam preprocessing cache as the cause.
- An explicit writable `AcquisitionStop` command was executed successfully and the handle was deinitialized, but the A6701-specific nodes remained unavailable. This excludes a merely orphaned acquisition state.
- The standard software reset changed the link-local camera address from `169.254.10.244` to `169.254.17.35`. Device identity remained `00111C0408CD`; software must continue binding by DeviceID rather than IP.
- No hard/factory-default, firmware-update, or manufacturing command was attempted because those operations can overwrite configuration or calibration.
- Production cleanup was hardened so every initialized-camera release attempts an idempotent device-side `AcquisitionStop` before `DeInit`, in addition to the normal `EndAcquisition` path.

## Reproduction after controlled power cycle

- The first initialization after a full A6701 power cycle returned a valid baseline: `CameraModel=A6701`, `Ready=1`, 640x513, `Mono16`, `Radiometric`, and readable synchronization nodes.
- The diagnostic executable then performed an exploratory scan over many vendor GenICam nodes. The following initialization reproduced `CameraModel='n]'` and unreadable A6701-specific nodes without starting acquisition or changing trigger configuration.
- This makes the exploratory all-node scan the leading software trigger. It has been removed. Production acquisition code does not perform an all-node scan.
- PowerShell output truncation was also removed from the hardware-test procedure so the native executable is always allowed to finish and release its camera handle.
- An obsolete incorrectly invoked probe process remained in an abnormal Windows terminating state and locked its old executable. Its command line proves it failed argument validation before camera initialization, so it is not evidence of a camera handle leak. A separately named allow-list-only `ppbng_a6701_health_check` executable was built successfully.
